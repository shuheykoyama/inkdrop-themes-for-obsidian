本実装は PoC（`research/poc/q-d21-build/`）とは別に、リポジトリ直下に置く。PoC は調査記録として残し、変更しない。

### 1.2 層と責務

| 層 | 置き場所 | 責務 | 書いてよいもの | 書いてはいけないもの |
|---|---|---|---|---|
| パレット | `src/palette/<theme>.css` | Inkdrop の宣言値の書き写し | `.theme-dark { --ink-*: <Inkdrop の宣言>; }`、HSL 三つ組のプリミティブ、出典コメント | Obsidian の変数、セレクタの工夫、値の換算 |
| マッピング | `src/common/mapping/` | Obsidian の公式変数（と未掲載の変数）に `--ink-*` を割り当てる | `--obsidian-var: var(--ink-*)` | 色のリテラル |
| コンポーネント | `src/common/components/` | 変数で表せない見た目を直接セレクタで補う | `selector { prop: var(--ink-*) }`、レイアウトに関わらない装飾 | 色のリテラル、テーマ名での分岐 |
| プラットフォーム | `src/common/platform/` | translucent とモバイルの条件付き上書き | 条件セレクタの下での変数の再代入・直接指定 | 不透明時の配色の変更 |
| エントリ | `src/themes/<theme>.css` | 連結順の定義 | `@import` だけ | 宣言 |

色のリテラルを書いてよいのはパレットだけとする（`transparent`・`currentColor`・`none` など Inkdrop の宣言そのものを除く）。静的テストで検査する（§3.1 S4）。

### 1.3 ビルド処理

- `scripts/build.mjs`: PoC の P1（`postcss` + `postcss-import` のみ）を引き継ぐ。警告を失敗として扱い、欠けたファイルは名前付きのエラーで非ゼロ終了する（13 で実証済み）。
- 追加する処理は 2 つだけ: 生成物の先頭のヘッダーコメント（テーマ名、元にした Inkdrop のリポジトリと SHA、「生成物なので直接編集しない」旨）と、`manifest.json` の配置。
- 色変換・minify・ネストの展開・autoprefixer は使わない（Q-D21）。ソースでは CSS ネストを使わない（モバイルの WebView での対応が未確認のため。13 §5）。必要になった場合は、ネストを使うかどうかを改めて判断する。
- Lint（計画レビューの指摘 PR-3 で改訂。§1.9）: 公式の `stylelint-config-obsidianmd` を生成物に掛ける。error は原則として修正し、warning は個別に評価して、必要なものだけ理由を記録して許容する。ルールの一括無効化はしない。

5. translucent（`.is-translucent:not(.is-fullscreen)` の条件付き）
6. モバイル（`.is-mobile` 系の条件付き）
7. テーマ固有の例外（あれば）

中間変数（`--ink-*`）は出力に残す（08 §5.1 の「中間変数を残す」。DevTools とスニペットで Inkdrop の名前から辿れる）。

### 1.5 出典情報と HSL 宣言値の保持

- 変数名: Inkdrop のトークン名に `--ink-` を付ける（例: `--editor-active-line-background-color` → `--ink-editor-active-line-background-color`）。acrylic の値は `-acrylic` を付けた別名にする（PoC と同じ）。HSL 三つ組のプリミティブ（`--hsl-*`、`--kanagawa-*`）は Inkdrop の名前を元にする。ただし、Inkdrop の名前に大文字を含むもの（例: `--kanagawa-dragonBlack1`）は、公式 lint の `custom-property-pattern`（kebab-case、error）に合わせて、大文字の前に `-` を入れて小文字にする（`--kanagawa-dragon-black1`）。変えるのは名前だけで、値は変えない。元の名前は宣言のコメントに残し、T1 は同じ規則で名前を対応させて照合する（工程 1 の lint 結果による変更。§1.9・§5）。
- 値: Inkdrop の宣言をそのまま書く（`hsl( var(--kanagawa-dragonBlack4) / 30% )` のように、空白も含めて元の表記に近づける。`var()` の参照先はパレット内の名前に置き換える）。`light-dark()` は dark 側の値を書き、そのことをコメントに残す。
- 出典: 各宣言の行末に `/* <repo>@<sha> <path>:<line> */` を付ける。SHA は `research/tools/sources.lock` と同じものを使う。
- 名前の衝突: パレットの変数名が Obsidian 1.14.4 の変数（`data/obsidian-css-variables-1.14.4.csv`）と重ならないことを静的テストで確認する。
- パレットを一次データ（`data/inkdrop-*-tokens.csv`）から自動生成するかは工程 2 で決める（09 §0.1.3）。手で書く場合も、T1 が CSV と全件照合するので、書き写しの誤りは検出できる（13 で実証済み）。

### 1.7 構造の共通化と値の分離

- 原則: 構造（どの Obsidian 変数・セレクタに、どの Inkdrop トークンを当てるか）は共通、値はパレット。2 テーマとも Inkdrop の同じトークン体系（基盤 `@inkdropapp/css` の変数名）を使うので、共通の構造は「Inkdrop トークン名 → Obsidian 要素」の対応として書ける。
- テーマ間で**値**が違うだけのもの（例: KD のガターの右線 `1px solid …` と SD の `none`）は、パレットの値の違いとして扱い、構造は共通にする。
- テーマ間で**構造**が違うもの（例: Inkdrop 側で片方のテーマだけが別のトークンを参照している、片方だけに規則がある）は、無理に共通化せず `src/themes/<theme>/` の例外ファイルに書く。例外ファイルには、どの Inkdrop の宣言の違いに対応するかを出典付きでコメントする。共通化によって片方のテーマの忠実度が下がることを避けるため（07 R18）。
- 片方のテーマにしかないトークンを共通の構造が参照しないことを、静的テストで確認する（参照先がパレットに無い変数を検出する。§3.1 S3）。

### 1.8 カスケードと詳細度の方針

既存の検証で確認済みの事実（11 §7、12 §4、13 §2.1・§2.1.1）を前提にする。

1. 変数の定義は `.theme-dark` で行う。`body` だけの定義は app.css の `.theme-dark` に負け、`body.theme-dark` の規則にはテーマの `.theme-dark` が負ける（V-01）。
2. 直接セレクタは、上書きしたい app.css の規則と同じ詳細度にし、読み込み順（app.css → テーマ）で勝たせる。詳細度を上げるときは、実在するクラスを足す（タブ帯の `.workspace-tabs`、ナビゲーションバーの `.mod-raised` と同じ方法）。`body` や `:is()` での水増しはしない。
3. `!important` は、app.css 側が `!important` を使っている箇所に限る（translucent 時のタブ帯と Ribbon、ガターの文字色が変数で変えられない場合など）。すべての `!important` を、上書き対象の app.css の規則と理由とともに許可リストに登録し、未登録の `!important` を静的テストで FAIL にする。許可リストは lint の warning の許可リストと共通（`tests/static/lint-allowlist.json`、§1.9）。
4. スコープを限定した変数の再代入（例: 中央の `.workspace-split.mod-root` での `--background-primary`）は、モーダル・ポップアウト・メニューに漏れないことを実行時テストで確認する（§3.5）。
5. app.css の規則を上書きするセレクタには、上書き対象の規則（app.css 1.14.4 の行番号）をコメントで付ける。Obsidian の更新時に、どの規則が前提かを辿るため。

### 1.9 stylelint の扱い（計画レビューの指摘 PR-3 で追加）

**確認した事実**（2026-10-11、npm registry と配布物の `index.js`・README を読んだ）:

- `stylelint-config-obsidianmd` は 0.1.0（唯一の版）。`stylelint` ^17.0.0 を peer に持ち、`stylelint-config-standard` ^40.0.0 を継承する。README は「error は投稿を止める、warning は止めない」と説明している。
- Obsidian 固有の規則のうち error は外部 URL の禁止（`function-url-scheme-disallowed-list` / `-allowed-list`）だけ。`declaration-no-important`・`color-named`・`selector-pseudo-class-disallowed-list`（`:has()`）・`plugin/no-unsupported-browser-features`（`electron >= 43`）などは **warning**。
- 継承した `stylelint-config-standard` の規則は既定の **error**（例: `custom-property-pattern`、`comment-empty-line-before`）。
- PoC（P1）の出力に掛けた結果: error 30 件（`custom-property-pattern` 16 件は Inkdrop の camelCase のプリミティブ名、残り 14 件は空行の書式）、warning 4 件（`declaration-no-important`）。

**方針**:

1. `.stylelintrc.json` は公式設定を `extends` するだけにする。ルールの一括無効化、ファイル単位・行単位の無効化コメント（`stylelint-disable`）は使わない。
2. error は修正する。名前の規則（`custom-property-pattern`）は §1.5 の名前の正規化で、書式の規則はソースの書式で直す。修正できない error が出た場合は、その時点で工程を止めて判断を仰ぐ（error を許容する仕組みは用意しない）。
3. warning は `tests/static/lint-allowlist.json` で個別に許容する。各項目に、規則名、対象（セレクタとプロパティ）、理由、関連する確定事項・検証記録を書く。許可リストにない warning と、出なくなった許可リストの項目（古い項目）は、どちらも静的テストの FAIL にする。
4. `!important` は §1.8 の方針どおり、app.css 側が `!important` を使う箇所に限る。`declaration-no-important` の warning の許可リストと、§1.8 の `important-allowlist.json` は同じものを指すように 1 つのファイルにまとめる（二重管理を避ける）。
5. ブラウザ対応の規則（`electron >= 43`、Obsidian 1.13.4 相当）は、最小対応版 1.14.0 より古い版を対象にするので、そのまま使う（より厳しい側）。

### 2.2 各工程

各工程の完了は、その工程で追加した検査がすべて PASS（FAIL 0 件）し、UNVERIFIED の項目が理由・リスク・確認に必要なものとともに記録されていることで判定する。「見た目が近い」だけでは完了にしない。**工程の完了はリリース可能を意味しない**（§2.3）。

#### 工程 1: ビルドシステム・検証基盤

- 範囲: §1.1 の骨組み、`build.mjs`、静的テスト（S1〜S6）、実行時テストのランナーと共通の判定関数、検査仕様の書式、視覚比較のスクリプト、`stylelint-config-obsidianmd` の導入、CI（静的テストだけ）。パレットとマッピングは、ランナーを動かすための最小のもの（PoC 相当）に留める。
- 完了条件:
  - クリーン環境の `npm ci` → ビルド → 静的テストが成功し、2 回のビルドがバイト単位で一致する。
  - 実行時テストのランナーが、存在しない要素・非表示の要素・値を取得できない要素を FAIL にすることを、わざと誤った検査仕様で確認する（自己テスト）。
  - 視覚比較のスクリプトが、V-04 の画像（`evidence/phase2-v04`）で 12 §7.2 と同じ数値を再現する。
- 検証: 静的テスト、ランナーの自己テスト、V-04 の数値の再計算。
- リスク: stylelint の公式設定が、計画している書き方（`!important`、未掲載クラスへの直接セレクタ）を禁止する可能性（未確認）。その場合は RV1 で、許可リストで抑止するか書き方を変えるかを判断する。

#### 工程 2: パレットと基本トークン

- 範囲: 両テーマのパレット全体（マッピングとコンポーネントが参照するすべての Inkdrop トークン。基盤から継承する値（Q-D9）と SD の base3 由来の値（Q-D3）を含む）。不透明と acrylic の両方。アクセントの h/s/l。パレットを自動生成するかの判断。
- 正本: `data/inkdrop-solarized-dark-tokens.csv`、`data/inkdrop-kanagawa-dragon-tokens.csv`（`source=theme` の行を優先し、ない場合は基盤の行）、acrylic は `conditional-overrides` の notes。
- 完了条件: T1 がパレットの全宣言で PASS（三つ組は文字単位、トークンは var 展開後、不透明は 8 ビット値でも照合）。他テーマの変数が混ざらない。Obsidian の変数名と衝突しない。どのトークンも、後の工程で参照されるか、参照予定の工程が記録されている。
- 検証: 静的テストのみ（Obsidian での確認は工程 3 以降）。
- リスク: Inkdrop の更新でトークンが変わる（§4 R-upstream）。自動生成にする場合、生成器の保守が増える。

#### 工程 3: デスクトップの基本 UI と背景マッピング

- 範囲:
  - **アクティブ行**: `.cm-line.cm-active` の背景 = `--ink-editor-active-line-background-color`。
  - **アクティブ行のガター**: `.cm-gutterElement.cm-active` の背景 = `--ink-editor-active-line-gutter-background-color`。
  - **行番号**: ガターの文字色 = `--ink-editor-gutter-color`（`.cm-gutters` 上で `--text-faint` を再定義する。V-07 で `!important` なしに変えられることを確認済み）。

  - **ガターの右線**: `--ink-editor-gutter-border-right`（SD `none`、KD `1px solid hsl(var(--kanagawa-dragonBlack4))`）。描き方は V-34 の結果で決める（`!important` 付きの `border-right` なら宣言値をそのまま使えて幅も Inkdrop と同じ。`box-shadow` なら `!important` が不要だが、宣言値の書き換えが要る）。

- 完了条件（すべて検査仕様に入れる）:
  1. 行番号を有効にした状態（テスト Vault の `showLineNumber: true`）で、Source mode と Live Preview のそれぞれで、アクティブ行の背景・アクティブ行のガターの背景・行番号の文字色・ガターの背景・ガターの右線が、両テーマとも Inkdrop の宣言値と一致する（要素が存在し、表示されていることを含む）。
  2. 色の一致と表示の連続性を**別々に**検証する（Q23-5a・Q23-5b）。どちらも、ネイティブのスクリーンショットの背景だけの平坦な領域（文字・行番号・KD の右線・アンチエイリアスの縁を除く）で測り、領域が平坦でなければ測定を無効（FAIL）とする。連続性の基準は境界をはさむ 2 領域の ΔE2000 1.0 以下（両者は同じ宣言値で、下地も同じエディタ面のため）。
  3. 行番号を無効にした状態（利用者の既定）で、アクティブ行のハイライトが出て、ガター関連の規則がレイアウトや他の要素に影響しない（ガターが存在しない、または非表示であることを検査仕様で明示的に期待する）。

  7. 長い行を折り返さない設定で横スクロールしたときのガターの背景を記録する（Inkdrop は不透明色に切り替えるが Obsidian に同じクラスがない。差がある場合は RV4 で扱いを判断する）。
- 検証: 実行時テスト（Computed Style）、ネイティブのスクリーンショット（連続性と重なり）、RV4 で V-30 の状態 4 と並べた視覚比較。

### 2.3 工程の完了条件とリリースの合格条件（計画レビューの指摘 PR-1 で追加）

2 つを分けて判定する。

| | 工程の完了条件（工程 1〜11 の各 RV） | リリースの合格条件（工程 11 の RV7 と工程 12） |
|---|---|---|
| 目的 | 次の工程に進めるか | 正式サポートとして配布できるか |
| FAIL | 0 件 | 0 件 |
| UNVERIFIED | 認める。ただし理由、リスク、確認に必要な環境・承認を記録する | **必須項目（§3.3 の `mandatory`）に 1 件でもあれば不合格** |
| PASS（EMULATED） | 進捗として記録してよい | 必須項目の合格に**数えない**。iOS・Android の phone / tablet（Q-D10）は実機の PASS が必要 |
| 対象範囲 | その工程の範囲 | 正式サポート範囲のすべて（Q-D10・Q-D20・Q-D22 など） |

- 正式サポート範囲を縮小する（例: 実機を用意できない端末を「未サポート」とする）かどうかは**ユーザーが判断する**。計画や実装の側で、未検証の範囲を黙ってサポート対象から外さない。
- Q-D10 の「デスクトップ」に Windows・Linux を含むかは、09 では明示されていない。現在の検証環境は macOS だけなので、リリースの合格条件に含める OS をユーザーに確認する（§4 R-desktop-os）。

### 3.2 実行時テスト（隔離 Obsidian、Computed Style）

- 方式: 13 の T3 と同じく、隔離インスタンス（CDP、127.0.0.1 のみ）に生成物を読み込み、Computed Style を測る。CSS の宣言（期待値）は生成物のパレットから計算する。
- **誤った PASS を防ぐ共通の判定**（13 §2.1.1 の教訓）:
  - 各検査は、要素の検索結果を `{ found, documents, displayed, size, value }` として返す。`found` が偽、`display: none`・`visibility: hidden`・寸法 0、値が取得できない・解釈できない場合は **FAIL**。
  - 「存在しないこと」「表示されないこと」を期待する場合は、検査仕様にその期待（`expect: absent` / `hidden`）と理由を明示的に書く。期待の明示がない不在は FAIL。
  - 比較は期待値（トークンの計算値）との一致で行う。「状態 A と状態 B で同じ」だけの比較は、両方が期待値と一致することを確かめた後にだけ使う（`null === null` を防ぐ）。
  - ポップアウトウィンドウ（Obsidian 1.14.4 の設定画面など）は、要素の `ownerDocument` の `getComputedStyle` で測る。
  - ランナー自身の自己テストとして、存在しないセレクタ・非表示の要素・誤った期待値を含む仕様で、FAIL になることを工程 1 で確認する。
- **詳細度が絡む規則の陰性対照**: `!important` 許可リストの規則と、app.css の規則に同じ詳細度で勝たせている規則は、その規則を外した生成物で検査が FAIL することを一度確認し、記録する（13 のナビゲーションバーの修正と同じ方法）。
- 結果の区分:

| 区分 | 意味 |
|---|---|
| PASS | 実機（macOS デスクトップ、または iOS・Android の実機）で確認した |
| PASS（EMULATED） | デスクトップの `app.emulateMobile` で確認した。**実機の確認の代わりにしない** |
| FAIL | 期待と違う、または要素・値が取得できない |
| UNVERIFIED | 確認していない。理由、リスク（確認しないまま進めた場合に何が起こりうるか）、確認に必要な環境・承認を書く。PASS としては数えない |
| N/A | 検査仕様で適用外と宣言した組み合わせ（例: Reading view のアクティブ行）。理由を書く |

### 3.3 検査仕様と検証マトリクス

**必須項目の一覧**（計画レビューの指摘 PR-2 で追加）: 確定済みの Q-D が定める重要な視覚的役割と表示状態（例: Q-D1 の各面の背景、Q-D22 の translucent 時の面、Q-D6 のアクセントの上書き、Q-D23 のアクティブ行・ガター・行番号）を `tests/spec/requirements.json` に 1 項目ずつ書く。各項目は、関連する Q-D、対象のプラットフォーム、`mandatory`（リリースの合格条件に入るか）、検証の手段（検査の ID の一覧）、または UNVERIFIED の理由とリスクを持つ。すべての CSS 宣言を必須項目にはしない。必須項目以外の宣言は、静的検査（S1〜S5）と代表的な実行時検査で守る。

検査仕様（`tests/spec/*.json`）は「どの要素が、どの状態で、どのトークンになるべきか」を 1 行ずつ書く。CSS の生成には使わない（構造を表で管理すると過剰設計になるため。08 §6）。書式は最小限にし、工程 1 では下の項目のうち `id`・`requirement`・`selector`・`document`・`property`・`token`・`appearance`・`expect`（と理由）だけを実装する。ビュー・プラットフォーム・設定・事前操作は、それを必要とする工程で足す。

| 項目 | 例 |
|---|---|
| `id` | `editor.active-line.bg` |
| `selector` / `document` | `.markdown-source-view.mod-cm6 .cm-line.cm-active` / `main` |
| `property` | `background-color` |
| `token` | `--ink-editor-active-line-background-color`（translucent 時の別トークンがあれば `token_translucent`） |
| `applies` | テーマ（両方 / 片方）、外観（不透明 / translucent）、ビュー（source / live / reading）、プラットフォーム（desktop / tablet / phone）、設定（`showLineNumber` など）、事前操作（カーソルを置く、検索する） |
| `expect` | `match`（既定）/ `absent` / `hidden`（理由が必須） |

マトリクスの軸と、全組み合わせを回さない方針:

| 軸 | 値 | 方針 |
|---|---|---|
| テーマ | SD / KD | 全検査で両方 |
| 外観 | 不透明 / translucent | translucent は macOS デスクトップだけ。translucent の対象は、条件付き上書きがある面と漏れ検査 |
| ビュー | Source / Live Preview / Reading | 要素が存在するビューだけ（例: アクティブ行は Source と Live Preview） |
| プラットフォーム | desktop / tablet / phone（フローティングナビ有効・無効） | モバイルの検査はモバイル固有の項目と、デスクトップと書き方が違う項目だけ |
| ユーザー設定 | アクセント、フォント、`showLineNumber`、長い行の折り返し | 設定に関係する検査だけ |

### 3.5 回帰検出（詳細度・スタイルの漏れ）

- 漏れの番人: スコープを限定した規則の外側にある要素（設定のポップアウト、クイックスイッチャー、コマンドパレット、メニュー、Popover、Canvas、ドラッグ中のオーバーレイ）を検査仕様に入れ、期待値と一致することを確認する。
- `body` レベルの変数（`--background-primary` など）が、translucent のスコープ変数で変わらないこと（13 の T3 と同じ）。
- 不透明 → translucent → 不透明で全領域が元に戻ること（13 の T3 と同じ）。
- `!important` 許可リストと app.css の対象規則の対応を、Obsidian の更新時に再確認する（§4）。

### 3.6 ユーザー設定との互換性

- アクセント: テスト Vault で `accentColor` を設定・解除し、利用者の値が勝ち、解除でテーマの値に戻る（13 の T3 と同じ）。
- フォント: 本文・UI・コードのフォントと基本のフォントサイズを設定し、利用者の値が勝つ（設定キーの名前は未確認。工程 5 で確認する）。
- 行番号・折り返し: §3.4。
- これらの設定変更は隔離インスタンスのテスト Vault でだけ行う。

### 3.7 視覚的比較

- 基準: Inkdrop の V-30（不透明、CDP のスクリーンショット、1024×800・倍率 1）、V-32（acrylic、ネイティブのキャプチャ）、V-35（Q-D23 の追加の基準、承認後に取得）。
- **撮影方法を揃える**: 不透明の比較では Obsidian 側も CDP のスクリーンショット（同じ寸法と倍率）を使い、translucent の比較では両方ともネイティブのキャプチャを使う。撮影方法が違う画像（CDP とネイティブ）は、色空間の扱いが違う可能性があるため直接比較しない（§5 の問題 6）。
- 比較の単位: 両アプリはレイアウトが違うため、画像全体の差分ではなく、対応する背景だけの平坦な領域の平均色を ΔE2000 で比べる（V-04 と同じ方法。V-04 の `sample-regions.py` を設定ファイルで領域と基準を渡せるようにして再利用する）。領域の標準偏差が閾値を超えた場合は、平坦でない（文字・境界線・アンチエイリアスが入っている）として測定を無効にし、FAIL とする。合否の基準は、不透明時の Computed Style の一致を主とし、画像は合成・重なり・不透明度の問題を見つける補助とする。
- 個人情報が写らないことを撮影ごとに目視で確認し、色の後処理をしない。

- 工程 10 の完了は実機の入手に依存する。実機がない場合、Q-D10 の「完全対応」は完了と言えない。
