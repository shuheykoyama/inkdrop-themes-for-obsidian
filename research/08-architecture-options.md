# 08. 実装アーキテクチャの選択肢

- 調査日: 2026-10-09
- 位置づけ: Phase 1 では**ディレクトリ構造とビルドツールを確定しない**。選択肢と評価軸、トレードオフ、暫定推奨を示し、確定は Phase 2 で行う。
- 前提（確定済み方針）
  - Solarized Dark と Kanagawa Dragon の 2 テーマを、独立した Obsidian テーマとして提供する。
  - Obsidian 公式 CSS 変数を優先し、足りない表現だけを DOM セレクタで補う。
  - 共通化は忠実度を損なわない範囲に限る。
  - 開発時にソースを分割・生成してもよいが、最終成果物は Obsidian ネイティブ形式（`manifest.json` + 単一の `theme.css`）にする。
  - macOS デスクトップを最優先の検証環境とする。

## 1. 最終成果物に課される制約（確認済み）

| 制約 | 内容 | 出典 |
|---|---|---|
| ファイル | テーマ 1 つにつき `manifest.json` と `theme.css`。Obsidian は固定のファイル名で読む | 03 §1.1（`app.js` の `ZT="theme.css"`） |
| 単一ファイル | `theme.css` は `<style>` の textContent として挿入される。相対パスの `@import` で別ファイルを読む構成は成立しないと考えられる（推測）。アセットのネットワーク読み込みは禁止 | 03 §2.3・§7 |
| リポジトリ単位 | `manifest.json` はリポジトリの HEAD に置き、タグと `version` を一致させた Release に `manifest.json` と `theme.css` を添付する | 03 §9.1 |
| テーマ数 | 1 リポジトリの HEAD に置ける `manifest.json` は 1 つなので、**directory に 2 テーマを載せるにはリポジトリが 2 つ必要**（推測。ドキュメントに 1 リポジトリ複数テーマの記述は見当たらない） | 03 §1.1・§9.1 |
| LICENSE | directory 投稿時に必須。GitHub が "Custom license" と判定すると警告 | 03 §1.1 |
| Lint | 公式 `stylelint-config-obsidianmd`（0.1.0、2026-07-31 公開）が自動レビューと同じ CSS ルールを強制する | 03 §10、npm registry（2026-10-09 取得） |

→ どの開発方式を採っても、**出力は「テーマごとに 1 つの `theme.css`」**になる。違いは開発時のソースの持ち方と生成方法にある。

## 3. 選択肢

### 3.1 案 A: 手書きの CSS（テーマごとに 1 ファイル）

各テーマの `theme.css` を直接書く。ビルドなし。

- 実例: Border、Things、既存 Kanagawa 2 種（04 §3〜§6）。
- 長所: 依存ゼロ（M3）。生成物 = ソースで可読性が高い（M4）。Obsidian の作法にそのまま従う。
- 短所: 2 テーマの共通構造（どの変数を埋めるか、直接セレクタ）を 2 か所で維持する（M1 が弱い）。Inkdrop のトークンとの対応はコメントでしか残せない（F1 が弱い）。

### 3.2 案 B: 分割した素の CSS を連結する

素の CSS で「パレット（テーマ別）」「マッピング層（共通）」「コンポーネント補完（共通）」を別ファイルに分け、単純な連結でテーマごとの `theme.css` を作る。連結はシェルの `cat` 程度で足りる。

- 長所: CSS の文法のまま書けるので、Lint や可読性が保たれる。依存がほぼない。共通構造を 1 か所で直せる（M1）。
- 短所: 値の差し込みは CSS 変数の参照（`var()`）に限られ、ループや条件分岐はない。テーマ間で構造が違う箇所（06 §3 の背景の奥行き、状態色の作り方）はパレット側で吸収する必要がある。
- 補足: マッピング層を `--color-base-00: var(--ink-editor-background)` のように**中間変数経由**で書けば、パレットだけを差し替えて 2 テーマを作れる。中間変数は出力に残る。

### 3.3 案 C: Sass / SCSS

パレットを Sass の map で持ち、`@use` / `@forward` でモジュール化し、ループや関数で変数群を生成する。

- 現行版: `sass` 1.105.1（npm、2026-09-29 公開）。`@import` は Dart Sass 1.80.0 で非推奨、3.0.0 で削除予定で、3.0.0 は 1.80.0 から 2 年以上後とされる（[sass-lang.com/d/import](https://sass-lang.com/d/import)、[blog](https://sass-lang.com/blog/import-is-deprecated/)）。
- 実例: Minimal（Dart Sass の JS API + build.js）、Catppuccin（sass CLI、7-1 パターン）、AnuPpuccin（`@import` 依存。非推奨化の影響を受ける）（04 §1・§2・§5）。
- 長所: map とループで、HSL 三つ組から `hsl()` やアルファ違いの色を機械的に作れる。テーマ間の差を変数とミックスインで表現できる（M1）。
- 短所: Sass の関数で色を計算すると、Inkdrop の宣言値（整数 % の HSL）と異なる丸めが入る可能性がある（F3 のリスク）。色はリテラルのまま渡し、計算はブラウザ側の `hsl()` / `color-mix()` に任せる運用が必要。Catppuccin の `_app-variables.scss` のように app.css の値を丸写しすると、本体更新で乖離する（04 §8 アンチパターン 1）。Node と Sass への依存（M3）。

### 3.4 案 D: PostCSS（素の CSS + 結合・変換プラグイン）

素の CSS 構文で書き、`postcss-import` でファイルを結合する。必要なら Lint の自動修正、ネスト展開、圧縮を追加する。

- 現行版: `postcss` 8.5.29（2026-10-05 公開）、`postcss-import` 17.0.0（2026-08-14 公開）、`postcss-nesting` 14.0.3（2026-10-05 公開、Node 20.19 以上）（npm registry、2026-10-09 取得）。
- 長所: ソースが標準 CSS のままなので、Obsidian の CSS をそのまま読み書きできる。stylelint との相性がよい（M5）。プラグインで後から機能を足せる。
- 短所: 案 B との差は「結合と変換の自動化」程度で、値の生成（ループ、テーマ別の分岐）は弱い。プラグインの組み合わせを保守する必要がある。
- 補足: ユーザー環境の Electron 39（Chromium 142）はネイティブの CSS ネストに対応している世代だが（Chromium 120 以降。本調査では一次情報で未確認）、Obsidian の stylelint 設定が `no-unsupported-browser-features` で何を基準にするかは未照合（03 §10）。

### 3.5 案 E: Lightning CSS

Rust 製の CSS 変換・結合・圧縮ツール。`@import` の結合、ネスト展開、圧縮、対象ブラウザに合わせた変換を 1 つで行う。

- 現行版: `lightningcss` 1.33.0（2026-07-20 公開、npm registry）。
- 長所: 単一ツールで結合と変換が完結し、高速。
- 短所: 対象ブラウザ指定によっては、`color-mix()` や `light-dark()` などをフォールバック値へ書き換える場合がある（推測。設定次第）。Obsidian テーマで既存の採用例は今回の調査範囲では見つかっていない。

### 3.6 案 F: トークン駆動の生成（データ → CSS）

Inkdrop 側の解決済みトークン（`palette.json`、または 02 の `data/inkdrop-*-tokens.csv`）と、マッピング表（06 の `data/mapping-candidates.csv` を発展させたもの）を入力にして、小さなスクリプト（Node または Python）で `theme.css` を生成する。必要なら出力を案 B〜E のいずれかに渡す。

- 根拠: Inkdrop の `palette.json` は `theme-dev-helpers` がブラウザで解決した computed 値で、02 の宣言値の解決結果と 1,638 / 1,638 件一致した（02 §1.5）。**Inkdrop 側が機械可読な正本を公開している**ので、これを直接入力にできる。
- 長所:
  - 追跡性（F1）が最も高い。生成物の各行に `/* inkdrop: --editor-background @ solarized-dark@4337f6e styles/ui.css:148 */` のような出典を自動で付けられる。
  - Inkdrop テーマが更新されたとき、再生成と差分確認で追随できる（M2）。
  - 値の丸めを避けられる（F3）。宣言値をそのまま出力すればよい。
- 短所:
  - 生成スクリプトという独自コードの保守が要る（M3）。
  - 直接セレクタ（R01）、Mermaid（R04）、トークンクラス（R02）などの「構造」は表で表しにくい。テンプレート化した CSS と組み合わせる必要がある。
  - 過剰設計になりやすい。マッピングの行数（06 で 97 行、うち変数のみで済むものは一部）に対して、生成器の複雑さが見合うかは要検討。

## 5. 方式と直交する設計判断

ビルドツールとは独立に決める必要がある。

### 5.1 パレットを出力に残すか（中間変数の有無）

| 方式 | 例 | 長所 | 短所 |
|---|---|---|---|
| 中間変数を残す | `.theme-dark { --ink-editor-bg: hsl(192deg 100% 8%); --background-primary: var(--ink-editor-bg); }` | DevTools やスニペットで Inkdrop 名で追える。ユーザーがスニペットで調整しやすい | 変数が増える。名前の衝突回避（接頭辞）が要る |
| リテラルに解決する | `.theme-dark { --background-primary: #002129; }` | 出力が簡潔 | 由来がコメント頼みになる |

04 §8 推奨 1・2（Minimal、Catppuccin）はいずれも中間変数を残す方式である。

### 5.2 色の記法

- Inkdrop は HSL 三つ組（`192deg 100% 8%`）を正本とする（02 §2）。Obsidian 1.13 以降は OKLCH の `color-mix()` を内部で使う（03 §0）。
- HSL の三つ組を中間変数に持てば、`hsl(var(--x) / 30%)` でアルファ違いを派生できる（04 §9）。Obsidian の `color-mix(in oklch, ...)` に合わせるかどうかは、ホバー色などの見え方の差として実機で確認する（09 V-05）。

### 5.3 リポジトリの構成

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| R1 モノレポ + 配布用リポジトリ 2 つ | 本リポジトリでソースを管理し、生成物を各テーマのリポジトリへ出す | 共通構造を 1 か所で管理。研究資料とソースが同居 | 配布リポジトリへの同期手順が要る |
| R2 テーマごとに独立リポジトリ | ソースも配布も各リポジトリ | directory の作法に素直 | 共通部分が二重管理になる |
| R3 本リポジトリのみ（directory に出さない） | 手動インストール、または BRAT 等で配布 | 最も単純 | directory に載らない |

Community directory に出すかどうかはユーザーの判断事項（09 Q-D16）。

### 5.4 共通化の単位

07 §16 のとおり、**共通化は「構造」（どの Obsidian 変数を埋めるか、どのセレクタを書くか）に限り、「値」はテーマごとに持つ**のが、忠実度と保守性を両立させる見込みが高い（推測）。背景の奥行き、状態色の作り方、エディタとプレビューの分岐は、テーマ別のパレット層で表現する。

## 6. 暫定推奨（Phase 2 で再評価する）

**推奨: 案 B（分割した素の CSS の連結）を基本とし、追跡性のために案 F の考え方（データからの生成と出典の自動付与）をパレット層に限って取り入れる。**

理由:

1. ビルド方式で再現範囲は変わらない（§4）。違いは保守性と追跡性なので、依存の少ない方式から始めて、必要になったら足す方が戻しやすい。
2. 2 テーマの共通構造は「マッピング層」と「コンポーネント補完層」に集約でき、値はパレット層で差し替えられる（04 §8 推奨 1、§5.4）。これは素の CSS と中間変数で実現できる。
3. Inkdrop 側に機械可読な正本（`palette.json`、02 の CSV）があるので、パレット層だけを生成すれば、丸め誤差のない値と出典コメントを得られる（F1・F3）。生成器の範囲をパレット層に限れば、独自コードの保守負担は小さい。
4. 出力が標準 CSS のままなので、公式 stylelint 設定で検査でき、directory の自動レビューでも読みやすい（M4・M5）。

採らなかった理由（暫定）:

- 案 C（Sass）: ループと map の利点はあるが、色の計算を Sass 側で行うと丸めの懸念があり、それを避けると利点の多くが消える。将来、生成量が増えたら再検討する。
- 案 D・E: 結合以外の変換（ネスト展開、圧縮）が必要になった時点で追加すればよい。現時点で必須の機能はない。
- 案 F の全面採用: 直接セレクタや Mermaid などの「構造」を表で管理するのは過剰設計になりやすい。

この推奨は、次の未確定事項に依存する。

- 09 Q-D16（directory に出すか）。出すならリポジトリ構成 R1 か R2 の決定が必要。
- 09 Q-D1・Q-D4・Q-D7 などの配色判断。テーマ間の構造差が大きくなれば、共通化の範囲は狭まる。
- 09 V-01 などの実機検証。詳細度の問題で `body.theme-dark` 等が必要になれば、マッピング層の書き方が変わる。
