## 2. 各判定の根拠と修正

### R-01 背景階層の縮約（ACCEPT）

**元の記述**: 「Inkdrop の 3 面（＋ page）を 2 段に縮約することになる」（07 R05、README、06 §2）。Q-D1 の選択肢はサイドバー色かノートリスト色かの二択だった。

**一次ソースでの確認**（app.css / app.js 1.14.4、静的解析）:

- 左右ドック本体の背景は `.workspace-tabs .workspace-leaf { background-color: var(--background-secondary) }`（L6912-6913）で、ノート領域は `.mod-root` 側の規則で `--background-primary`（L6909-6910、L4663-4664）。公式変数だけなら、ペイン本体の地色は 2 色である。
- 帯は別の変数で塗れる。Ribbon は `--ribbon-background`（L4794）、タブ帯と分割の地は `--tab-container-background`（L6661-6663、L6920）、ドックのタブ帯は `--sidebar-tab-container-background`（L6931-6932、docs 未掲載）、タイトルバーとステータスバーにも専用変数がある。
- app.js はサイドドックに `mod-sidedock` と、論理名（`mod-primary-split` / `mod-secondary-split`）と物理名（`mod-left-split` / `mod-right-split`）の両方を付ける（`addClass.apply(o,k(["mod-sidedock"],AS(i,"mod-{side}-split")))`、`AS` は `TS` と `DS` の両方を返す）。各ビューには `data-type`（`file-explorer` など）が付く。
- CSS Custom Properties の仕様では、カスタムプロパティの計算値は変数を置換した指定値で、宣言された要素の上で解決され、子孫はその計算値を継承する。したがって `.workspace-split.mod-left-split { --background-secondary: X }` は、その要素と子孫で `var(--background-secondary)` を参照する箇所にだけ効き、`body` の上で計算値が確定した `--tab-container-background` などは変わらない。

**判断**: 指摘は正しい。「公式変数の基本構造が 2 段」と「テーマで表現できる背景色が 2 段」は別の話で、後者は誤りだった。ただし、Inkdrop の横並びの 2 ペインという**構造**は、File Explorer が 1 本のツリーである以上、テーマ CSS では作れない。この 2 つを区別した。

**対応の途中で見つかった制約**（Phase 1B の批判的レビューによる。§3 参照）: 最初の修正案は、新しく示した手段の実現性を楽観的に書きすぎていた。

- `mod-primary-split` と `--sidebar-tab-container-background` は 1.14 以降にしかない。1.13.7 の app.js は `mod-left-split` / `mod-right-split` だけを付ける。
- 各分割の最上段のタブグループ（`.workspace-tabs.mod-top`）では、両方のタブ帯変数が `--titlebar-background` に置き換わる（L4354-4358）。そのためドックのタブ帯は、通常はタイトルバーの色と連動する。

これらを 07 R05 の表（「対応版」列を追加）、05、06、09 Q-D1・V-03・V-16、README に反映し、Q-D1 が Q-D20（`minAppVersion`）に依存することを明記した。

**修正**: 07 R05（事実・影響・手段の表・副作用）、06 §2・§3 と W03・W04、05 Workspace 節、09 Q-D1（選択肢 (d)〜(f) と判断材料、保守リスク、Q-D20 への依存）、09 V-03・V-16、README の発見 1。

### R-02 シンタックスハイライトの完全一致（PARTIAL）

**元の記述**: 「Obsidian の `--code-*` は 10 色しかなく、同じ変数が Reading と編集時で別のトークンを指すため、完全一致は不可能」。

**一次ソースでの確認**:

- docs 原文（`Editor/Code.md:17-18`、公開版も同文）は "styling may not match perfectly between the two" で、不可能とは書いていない。
- 編集ビューは CM5 のモードを CM6 の StreamLanguage で動かし、トークン名に `cm-` を付けてクラスにしている（app.js の `StreamLanguage:()=>wp`、`wp.define(CodeMirror.getMode({},{name:"hypermd"}))`、`"cm-"+e`）。言語モードは `lib/codemirror/modes.min.js`（`defineMode("…")` の呼び出し 119 個）。閲覧ビューは Prism（`lib/prism.min.js`）。
- 直接セレクタを使えば、「10 色しかない」「変数の意味が両ビューで違う」という制約は回避できる。`.cm-def` / `.cm-atom` のように既定で無色のクラスも塗れる。
- 一方で、Obsidian 側のトークナイザが同じクラスを出す箇所は CSS で区別できない。静的解析で次を確認した（03 §6.3）: 編集時 JS の関数呼び出しと変数参照（どちらも `cm-variable`）、メソッド呼び出しとプロパティ参照（どちらも `cm-property`）、閲覧時 JS の `this` と `const`（どちらも `token keyword`）、閲覧時 Python の関数呼び出し（span なし）。

**判断**: 指摘の「公式変数の限界と、直接セレクタを使った場合の限界は別」という点は正しく、Phase 1 の根拠は誤りだった。しかし、指摘が示唆する「完全一致は未検証であり、実装方式と言語ごとのトークン粒度に依存する」という書き方だけでは、静的解析で示せた**区別できない例**が抜け落ちる。そこで、(1) 公式変数だけでは不可、(2) 直接セレクタで一致度は上げられるが、トークナイザの粒度による上限があり、具体例がある、(3) 全体の一致度は言語ごとに未検証、の 3 点を併記した。

**残る不確実性**: Inkdrop 側の `tok-*` クラスの付き方は、`syntax.css` の構造からの推定である（tokenHighlighter は npm にも公開されていない）。上の例が実機の DOM でも成り立つかも未確認（09 V-12・V-31、U-12）。

**修正**: 03 §6.3（原文の引用、トークナイザ、区別できない例、行番号を L12031–L12097 / L12098–L12139 に訂正）、07 R02、06 E21、09 Q-D13・V-12・V-31・U-12、README の発見 4。

### R-03 Sass の値精度（ACCEPT）

**元の記述**: 08 §3.3「Sass の関数で色を計算すると、Inkdrop の宣言値と異なる丸めが入る可能性がある」、§4 の F3 で △。

**確認**: `sass` 1.105.1 を `npx` で一時実行した（リポジトリには何も追加していない）。`hsl(45deg 7% 11%)` はそのまま出力され、Sass 変数経由でも `hsl(45, 7%, 11%)` で HEX には丸められなかった。`color.mix()` の結果は `rgb(20.593%, 20.2465%, 19.207%)` のように小数で出力された。

**判断**: Phase 1 の評価は確かめずに書いた推測で、誤りだった。比較の公平性のため、Lightning CSS（1.33.0）も同じ条件で試し、こちらは既定で `hsl()` を `#1e1d1a` に変換し、`color-mix()` を `oklch()` に置き換えることを確認した（F3 の △ は維持）。

**修正**: 08 §3.3・§3.5・§4・§6（案 C を退けた理由の 1 つが成り立たないこと）、09 Q-D21。

### R-04 `<style>` の textContent と相対 `@import`（PARTIAL）

**元の記述**: 08 §1「`theme.css` は `<style>` の textContent として挿入される。相対パスの `@import` で別ファイルを読む構成は成立しないと考えられる（推測）」。

**確認**:

- app.js の `loadTheme` は、`this.loadCss(this.getThemePath(i))` で読んだ文字列を `n.textContent=r` で `<style>` 要素に入れている。
- HTML Standard の「update a style block」では、`<style>` から作られるスタイルシートは location を持たない。
- CSS Values 4 §4.5.1 は、文書に埋め込まれたスタイルシートの相対 URL がコンテナのベース URL で解決されると定めている。Obsidian では `index.html` の URL になる。

**判断**: 結論（テーマフォルダを基準にした相対 `@import` は、テーマフォルダのファイルを指さない）は仕様から導けるので維持した。ただし Phase 1 の書き方は根拠が「推測」だけで、`@import` 全般が不可能とも読めたため、根拠を仕様に差し替え、絶対 URL の `@import` は仕様上可能だがガイドラインが禁じている、と書き分けた。実機での確認は 09 V-15 に残した。

**修正**: 08 §1・未確認事項 2、09 V-15。

### R-05 HSL→HEX の計算値と描画色（ACCEPT、範囲を拡大）

**元の記述**: 02 §2.2「レンダリング色はコメントの HEX から最大 2/255 ずれる」、README「実際に描画されるのは HSL 宣言から計算した `#1e1d1a`」など。

**確認**:

- `#1e1d1a` は Python の `colorsys` で HSL を sRGB に変換し、8 ビットに丸めた計算値である。描画色は測っていない。
- さらに、Inkdrop の `palette.json` を確認したところ、値は `hsl(45deg 7% 11%)` のような文字列のままだった。theme-dev-helpers のソースでは、`var()` の展開はブラウザの `computedStyleMap()`、`light-dark()` の分岐はツールの文字列処理（`resolveLightDark`、`palette.ts:246-263`）、`color-mix()` はブラウザで計算して置換している。両テーマには `color-mix()` 由来の値がない。Phase 1 は `palette.json` を「ブラウザで抽出した computed 値」と書き、1,638 件の一致が実アプリの値の裏付けであるかのように読める記述をしていた。

**判断**: 指摘は正しい。加えて、`palette.json` との一致が示すのは「本調査の解決スクリプトと harness の結果（`var()` の展開と、別実装の文字列処理による分岐選択）の一致」までで、実アプリ上の値や描画色ではないことを明記した（自己発見。批判的レビューで、分岐選択がブラウザではなくツールの処理であることの指摘を受けて精度を上げた）。忠実度の観点では、Obsidian 側でも同じ `hsl()` 宣言を書けば両アプリが同じ Chromium の変換を通るため、HEX への換算そのものが不要になる、という整理も加えた（ただし両アプリの Chromium 版と色管理が同じかは未確認）。

**修正**: 02 凡例・§1.5・§2.2・§12、07 R14・§14、08 §3.6、00 §6、09 Q-D2・V-29、README（発見 2、表記の約束）。

### R-07 分類と確信度の定義（ACCEPT）

**元の記述**: 06 §1 は「Inkdrop 側の消費箇所が非公開のトークンは確信度を下げる」「High = 適用先も公開ソースで確認できる」と定義していた。一方で W05（エディタ背景）、E04（キャレット）など、消費箇所が非公開のトークンを High にしていた。G02（拡張色）は色名で対応付けており、06 §1 の原則 1（色名で対応付けない）と矛盾していた。

**確認**: 01 の `inkdrop-base-tokens.csv` の `consumers=` 注記から、各行の Inkdrop トークンが公開ソースで消費されているかを機械的に判定した。公開 43 行、非公開 29 行、混在 13 行、トークンなし 12 行だった。

**修正**: 06 §1（定義と新列の説明）、`mapping-candidates.csv` に `inkdrop_consumer` 列を追加、G02 の分類と確信度。分類は Direct 49 → 48、Semantic 32 → 33、確信度は High 37 → 36、Medium 47 → 48（G02 の変更による）。
